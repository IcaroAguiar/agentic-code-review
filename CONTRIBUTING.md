# Contributing

Agentic Code Review is a review skill and toolbelt for production code generated by agents. Contributions should improve review signal quality, reduce false positives, or extend language/framework coverage without turning the deterministic scanner into the final approval gate.

## Pull Request Shape

- Prefer small PRs with one responsibility.
- Target 200-400 changed LOC when practical. Larger PRs need a short rationale and clearer verification evidence.
- Keep generated files, local artifacts, fixture churn, and unrelated refactors out of the diff.
- Include or update smoke fixtures when a rule changes.
- Keep DAST, load tests, downloads, and autofix behavior opt-in.

## Engineering Principles

- Rules should be language-agnostic when possible and framework-aware when useful.
- A deterministic finding is evidence, not proof. Avoid wording that says a scanner result alone approves or rejects a PR.
- Prefer concrete, high-impact signals: correctness, public contract integrity, security boundary risk, data consistency, N+1, testability, accessibility, and runtime proof gaps.
- Calibrate noisy heuristics with real PRs before raising severity.
- Keep sensitive output redacted. Do not print secrets, cookies, tokens, or full environment files.

## Web/API Review Standards

- REST endpoints should model resources with nouns, use HTTP methods for semantics, expose explicit status codes, and define pagination/filter contracts for collections.
- Public APIs should have a versioning strategy and OpenAPI/consumer compatibility evidence when contract shape changes.
- UI checks should prioritize semantic landmarks, labels, image alternatives, keyboard reachability, and correct `button` versus `a` semantics.
- Accessibility tooling such as `eslint-plugin-jsx-a11y`, Testing Library role queries, axe, or framework-native equivalents should complement browser-use evidence.

## Verification Before Merge

Before merging a contribution:

1. Run the smoke suite.
2. Run `git diff --check`.
3. Run `npm pack --dry-run` when packaging/install behavior changed.
4. For scanner behavior changes, calibrate against at least one real repository or explain why a fixture-only validation is sufficient.
5. If the change touches executable behavior, exercise the real production path where feasible.

Reviewer-facing validation should describe the behavior tested and risk protected. Do not paste command dumps as the main evidence.
